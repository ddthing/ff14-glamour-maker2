# 전체 리팩터링·리디자인 검수 및 제안서

검수일: 2026-09-06 · 대상: 현재 로컬 작업본 · 제안 단계, 제품 코드 변경 없음

## 1. 결론

**현재 상태는 공개 배포 승인 불가다.** 개별 컨트롤 검증은 진행됐지만, 카드별 데이터 독립성·삭제 후 복구·최종 출력 일치라는 편집기의 핵심 계약이 완성되지 않았다. 시각적으로는 작은 글자, 긴 속성 패널, 서로 다른 슬라이더 표현이 남아 있다. 전체 리팩터링은 필요하며, 저장 모델부터 순차적으로 교체해야 한다.

이전 보고의 “전체 검증 통과”, “미리보기·PNG 동일 적용”, “수동 검수와 배포 연결만 남음”을 전체 제품 품질의 보증으로 사용하면 안 된다. 이번 검수에서 기존 검사가 다루지 않은 오류를 재현했다.

실제 외부 시니어 전문가의 승인 보고가 아니다. 본 에이전트가 개발·디자인·제품 커뮤니케이션의 관점으로 코드와 로컬 브라우저를 검수한 결과다. 이전 별도 감사 의견은 배경 자료이며 이번 변경본의 재승인으로 취급하지 않았다.

## 2. 검수 범위와 증거

- 코드: app.js, HTML, CSS 네 파일, Node 정적 서버, Pages 배경 제거 프록시, 저장·삭제·이력·내보내기 경로 및 관련 검사.
- 문서: DESIGN.md, README, 진행 현황, 배포 안내, 접근성 검토 기록.
- 실제 Edge: 독립 브라우저 컨텍스트에서 이미지 업로드 → 새 룩 → 카드 비우기 → 되돌리기 → 새로고침을 수행했다. 사용자 브라우저의 기존 데이터를 조작하지 않았다.
- 화면: 1440×1000 데스크톱, 390×844 모바일. 검사용 이미지는 메모리에서 만든 단색 PNG이며 운영 assets에 추가하지 않았다.
- 코드 규모: app.js 약 3,350줄, CSS 약 8,280줄(줄 분리 기준), CSS !important 81회. 이것만으로 결함이라 판단하지 않고 책임 중복과 결합도를 함께 확인했다.
- 이번에는 기존 전체 회귀를 반복 실행하지 않았다. 이전 통과 결과의 커버리지를 확인하고, 누락된 사용자 시나리오를 별도로 실행했다.

재현 도구: [strict-audit.cjs](../artifacts/strict-audit.cjs). artifacts/strict-audit.json은 구현 후 재실행으로 갱신되었으므로 최초 검수의 원시 증거로 인용하지 않는다. 이 문서의 발견 사항은 제안 당시 기록이며, 최신 검증 범위는 구현 기록을 따른다. artifacts는 Git 제외된 로컬 QA 기록이다.

## 3. 우선순위별 발견 사항

### P0-01. 새 룩이 이전 룩의 이미지를 그대로 사용한다 — 브라우저 재현

재현: 카드 A에 audit-A.png 업로드 → LOOK BOOK 펼치기 → 새 룩 생성. 새 룩에도 audit-A.png 이미지 한 장이 표시됐다. 저장된 두 look 객체에는 characters 필드가 없었다.

근거: app.js:717의 syncStateIntoLook, :1093의 serializeLook은 이미지·인원수·배치를 저장하지 않는다. :1109의 saveState는 characters와 characterCount, 비율 등을 작업공간 최상위에 저장한다. :2055의 selectLook도 해당 상태를 카드별로 교체하지 않는다.

영향: 새 작품에 이전 사진이 나타나고, 한 작품의 사진 변경·초기화가 다른 작품에 영향을 준다. LOOK BOOK을 저장된 작품 목록으로 신뢰할 수 없다.

제안: 각 Look이 characters, layout, copy, background, effects를 소유하도록 변경한다. 작업공간에는 선택 카드 ID와 탐색 환경설정만 둔다. 새 룩은 독립된 빈 객체를 만든다.

완료 기준: A/B에 다른 사진·인원수·비율·배치를 설정하고 10회 전환, 새로고침, A만 비우기를 실행해도 B가 변하지 않아야 한다.

### P0-02. “되돌리기로 복원” 안내와 달리 이미지 복구가 실패한다 — 브라우저 재현

재현: 이미지 업로드 → 현재 카드 비우기 → 되돌리기. 이미지 DOM은 복구되지만 naturalWidth가 0이었다. 새로고침하면 이미지가 사라졌다.

근거: app.js:2763의 resetCardData가 URL을 revoke하고 IndexedDB 자산을 삭제한다. :1204의 restoreSnapshot은 이미 무효화된 blob URL을 복사한다. 업로드 교체도 :2094에서 기존 URL을 폐기하고 같은 assetKey의 원본을 덮어써, 이력과 자산 수명이 분리돼 있다.

제안: 현재 카드 비우기는 논리 삭제하고, 살아 있는 카드 및 실행 취소 이력에서 참조되지 않을 때 자산을 회수한다. 전체 로컬 삭제는 별도의 영구 삭제로 처리하고 되돌릴 수 없음을 실행 전에 명확히 표시한다. 이미지 교체 시 새 asset ID를 부여한다.

완료 기준: 업로드 교체·카드 비우기의 undo/redo에서 실제 이미지 디코딩 성공과 새로고침 후 선택된 결과까지 검사한다. 버튼 활성화만 검사해서는 안 된다.

### P1-03. 제목 미리보기와 PNG의 처리 규칙이 다르다 — 코드 확인, 출력 재현 미완료

app.js:1283의 fitBoardTitle은 글자를 축소하고 줄바꿈한다. :2507의 fitText와 :2513의 drawTitle은 고정 크기로 그리며 긴 문장을 말줄임한다. 제목 외곽선도 CSS px와 내보내기 논리 좌표의 px를 직접 사용해 화면 축척에 따른 시각적 비율 검증이 필요하다.

이번 브라우저에서 64자 제목·6px 외곽선은 미리보기에 적용됐다. PNG 다운로드는 두 차례 30초 대기 내 완료되지 않았고, 마지막 짧은 재현에서는 텍스트 그리기 호출도 기록되지 않았다. 원인이 폰트 대기인지 다른 비동기 처리인지 확정하지 않았다. 따라서 실제 PNG 픽셀 불일치의 재현 성공으로 표현하지 않는다.

제안: 공통 논리 좌표계에서 제목 줄바꿈·글자 크기·글리프 외곽선을 계산하고 DOM과 Canvas가 같은 결과를 사용한다. 내보내기는 클릭 시점의 불변 카드 스냅샷을 받아 실행한다. 폰트 준비·출력 중·실패 상태와 제한된 대기 정책을 둔다.

완료 기준: 1/2/5인, 세로/가로, 짧은/64자 제목, 0/3/6 외곽선에서 다운로드한 PNG를 열어 문구 누락과 배치·비율을 비교한다.

### P1-04. 저장·삭제 실패를 성공처럼 숨길 수 있다 — 코드 확인

saveState는 localStorage 쓰기 실패를 조용히 무시한다. resetWorkspace는 IndexedDB clear 실패를 무시한 후 전체 삭제 완료를 안내한다. 저장 불가와 삭제 미완료를 사용자가 알 수 없다.

제안: 저장 상태를 저장 중/저장됨/저장 실패로 표시한다. 전체 삭제는 완료된 저장소와 실패한 저장소를 구분하고 재시도를 제공한다. 이미지 작업의 진행 중 저장이 초기화 이후 다시 반영되는 경쟁 조건도 테스트한다.

완료 기준: 용량 부족·쓰기 거부·DB 삭제 실패를 주입해도 거짓 성공 안내가 없고, 작업을 보존하거나 복구 방법을 안내해야 한다.

### P1-05. 제목 외곽선 슬라이더가 공통 조작 디자인을 따르지 않는다 — 화면 확인

[390px 실제 컨트롤 화면](../artifacts/audit-controls.png)에서 트랙이 24px 높이의 두꺼운 막대이고 손잡이는 작은 사각형이다. 색상 원형 버튼, 서체 굵기 카드, 프레임 세그먼트와 조작 형태가 분산돼 있다.

근거: styles.css:1484는 range 요소 자체에 배경과 appearance:none을 적용한다. styles/editor-controls.css:2518은 제목 외곽선 range 높이만 24px로 확장한다. 이미지 편집 range는 별도 track/thumb 스타일을 가진다.

제안: Slider 공통 규칙을 만들고 트랙 4px, 손잡이 18~20px, 조작 영역 40~44px를 분리한다. 제목 외곽선에는 없음/켜짐, 색상, 두께와 수치 직접 입력을 같은 그룹으로 제공한다. 수치는 제안 토큰이며 아직 DESIGN.md에 반영하지 않았다.

완료 기준: 크기·위치·그림자·외곽선 슬라이더의 시각·키보드·포커스·드래그 동작이 같아야 한다.

### P1-06. 작은 글자와 긴 모바일 패널이 결과 확인을 어렵게 한다 — 화면·스타일 확인

실제 계산 스타일에서 프레임 옵션 9px, 이미지 안내 8px, 제목 서체 보조 문구 9px, 배경 선택 이름 8px가 확인됐다. 모바일 전체 문서는 약 2,964px 높이였고 문구·배경을 편집할 때 위쪽 카드가 시야 밖에 있었다. 가로 넘침이 없다는 검사만으로 편집 편의성을 보장할 수 없다.

제안: UI 기본 14px, 보조 12px, 섹션 제목 16px를 출발점으로 검증한다. 작은 글꼴을 곧 WCAG 위반으로 단정하지 않는다. 캔버스 작품의 글자 크기는 UI와 별도로 판단한다.

모바일은 상단의 크기 제한된 미리보기와 하단의 현재 작업 패널로 구성한다. 화면이 낮거나 키보드가 열리면 미리보기를 축소·접을 수 있도록 한다. 이미지 위치 편집은 실제 카드에 직접 적용하고, 도크 높이를 레이아웃에 반영해 선택 영역이 가려지지 않게 한다.

완료 기준: 320/390/768/1024/1440px 및 높이가 낮은 화면에서 제목·배경·배치 변경 결과를 곧바로 확인할 수 있어야 한다. 키보드 등장과 200% 확대도 포함한다.

### P1-07. 테스트가 결과보다 내부 상태를 증명한다 — 검사 코드 확인

- check-info-reset.cjs는 비우기 후 undo 버튼이 활성인지 검사하지만 실제 undo 후 이미지 디코딩을 검사하지 않는다.
- check-title-outline.cjs는 CSS·저장값을 검사하며 PNG를 다운로드하지 않는다.
- check-title-halo.cjs는 위 검사를 다시 호출하는 별칭이다. 파일 28개 실행을 독립 시나리오 28개로 세면 안 된다.
- check-style-seams.ps1은 중괄호 수·일부 문자열·로드 순서를 검사한다. CSS 중복, 우선순위 충돌, 책임 분리를 완전히 보장하지 않는다.
- 루트 package.json·잠금 파일·공통 테스트 실행 설정이 없고 외부 PLAYWRIGHT_MODULE 및 설치된 Edge 경로에 의존한다.

제안: 로컬에서 재현 가능한 실행 환경과 실패 증거 수집을 정리하고, 핵심 사용자 결과를 테스트의 합격 기준으로 바꾼다. 테스트 개수보다 요구사항별로 무엇이 검증됐는지 보고한다.

### P1-08. 배포 안내와 공개 파일 경계가 불완전하다 — 코드·문서 확인

docs/cloudflare-deployment.md:20의 배포 목록에는 index.html이 참조하는 styles/ 디렉터리가 빠져 있다. 이 목록대로 패키징하면 분리된 CSS가 누락된다. Node 서버는 server.js:596 이후 루트 내부 파일을 확장자 허용 목록 없이 제공하고 :615에서 host를 지정하지 않는다. 실제 외부 노출 여부는 방화벽·실행 환경에 따라 달라지며 이번에는 검사하지 않았다.

제안: 배포용 디렉터리를 명시적으로 생성하고 CSS·폰트·데이터 및 Functions를 포함하는 manifest를 검증한다. 로컬 정적 서버는 공개 파일 허용 목록과 기본 loopback 바인딩을 적용한다. 잘못된 URL 인코딩 등 요청 오류는 요청 단위로 처리한다.

완료 기준: 새 배포 디렉터리만으로 페이지와 모든 필수 CSS가 200 응답하고, 소스·설정·로컬 QA 파일은 공개 경로에서 제공되지 않아야 한다.

### P2-09. 디자인 계약과 기본값·용어가 어긋난다 — 코드·화면 확인

DESIGN.md는 새 카드 Pretendard를 지정하지만 app.js:103은 기본 제목을 gmarket-sans로 설정한다. UI 자체의 Pretendard 정책과 제목 선택 서체는 구분해야 한다. 부위는 모자/티셔츠 등의 텍스트 배지가 됐으며 요청했던 직관적인 도상 아이콘을 완성한 상태는 아니다. 헤더의 언어 선택은 전체 앱 번역처럼 보이지만 설명상 장비·카드 언어 기능이다.

제안: 새 제목은 Pretendard, 다른 서체는 명시적 선택으로 제공한다. 장비 편집에 동일 계열의 모자·상의·장갑·바지·신발 아이콘과 텍스트를 함께 적용한다. 언어는 실제 적용 범위를 이름으로 밝힌다. LOOK BOOK에는 작품 썸네일·이름·저장 상태를 보여주고 새 카드/복제/이름 변경/삭제를 일관되게 배치한다.

### P2-10. 파일 분리보다 상태·렌더링 책임 분리가 먼저다 — 구조 판단

app.js에 저장, 이력, 검색, 비동기 이미지 처리, DOM 렌더링, PNG 출력이 함께 있다. CSS는 파일을 나눴지만 과거 스타일과 최종 덮어쓰기 방식이 누적돼 있다. 여러 render 함수의 호출 순서를 알아야 올바르게 업데이트할 수 있는 구조다.

제안: 동작 단위 모듈을 추출하고 기존 경로를 제거한다. 같은 이름의 함수만 여러 파일로 이동하거나 기존 CSS 위에 새 덮어쓰기를 추가하는 작업은 완료로 인정하지 않는다.

| 헤더 | 서비스명, 카드 이름/저장 상태, PNG 내보내기. 언어는 적용 범위가 드러나는 위치·이름으로 정리 |
| LOOK BOOK | 기본 접힘 유지. 펼치면 작품 썸네일·이름·정리 동작. 작품 데이터가 독립적으로 저장된 뒤 제공 |
| 데스크톱 | 중앙 미리보기와 약 320~360px 속성 패널. 현재 대상은 이미지/문구/배경/장비로 구분 |
| 이미지 | 업로드 전 하나의 명확한 추가 행동. 업로드 후 원본/배경 제거, 직접 배치. 크기 기본 노출, 좌표는 세부 조정 |
| 문구 | 제목·설명 입력과 서체·굵기·외곽선을 같은 편집 맥락에 배치 |
| 배경 | 단색·패턴·질감을 같은 크기·반경·선택 표시로 통일. 작은 이중 테두리를 누적하지 않음 |
| 장비 | 부위 아이콘+이름, 검색, 현재 선택 아이템. 빈 상태에 가짜 정보 없음 |
| 모바일 | 미리보기와 선택 패널을 제한된 높이 안에 배치. 키보드가 열릴 때 입력과 적용 상태 우선 |
| 초기화 | 스타일 복원/현재 카드 비우기/전체 데이터 삭제를 분명히 구별. 가장 위험한 실행은 내용과 범위를 확인한 뒤 수행 |

모션은 120~180ms 선택 피드백, 180~240ms 패널 전환을 출발점으로 삼는다. 이미지 드래그는 지연 없이 즉시 반영하고, 캐릭터 선택 시 색상·필터를 보간하지 않는다. 로딩은 실제 진행 상태를 보여주고 reduced-motion에서는 위치 이동 애니메이션을 줄인다. 이는 제안 수치이며 전면 애니메이션 추가를 의미하지 않는다.

접근성은 프로젝트 조작 영역 목표를 40~44px로 잡되, WCAG 2.2 AA의 최소 포인터 목표는 24×24 CSS px 또는 명시된 예외 조건이라는 점을 구분한다. [W3C 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html). 저장·오류 상태는 포커스를 빼앗지 않고 보조기술에도 전달한다. [W3C 4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html).

## 5. 리팩터링 구조

| 모듈 | 책임 | 검증할 계약 |
| --- | --- | --- |
| Workspace / Look | 카드 생성·선택·수정·복제·삭제 | 카드 간 독립성, 직렬화 왕복 |
| AssetStore | 원본·결과 이미지와 참조 수명 | 이력 복구, 자산 회수, 저장 실패 |
| History | 카드별 편집 트랜잭션 | 연속 슬라이더 1회 취소, 이미지 교체 복원 |
| Composition | 정규 좌표, 텍스트 맞춤, 레이어 | DOM/PNG에 같은 배치 제공 |
| Export | 불변 스냅샷과 폰트·자산 준비, PNG 생성 | 글자 누락 없음, 규격과 오류 상태 |
| Editor UI | 선택·포커스·진행 표시와 공통 조작 | 키보드·터치·반응형·비동기 응답 격리 |
| ItemSearch / Cutout | 취소·제한 시간·오류 정규화 | 오래된 결과가 새 카드에 반영되지 않음 |

현재 규모에서 React/Next.js 전면 교체를 선행 조건으로 삼을 근거는 부족하다. 우선 native ES modules와 명시적 데이터 계약으로 분리하고, UI 구현 수단의 변경은 복잡도 감소가 확인될 때 결정한다.

저장 스키마를 바꿀 때 모든 기존 데이터를 무조건 버리지 않는다. 현재 v3의 공용 이미지가 어느 룩에 속했는지 추론할 수 없으므로 선택된 룩으로 보존하고 나머지 룩의 복구 한계를 명시한다. 마이그레이션 성공 전 원본 저장 기록을 유지하고, 테스트 데이터 제거는 운영 데이터 마이그레이션과 구별한다.

## 6. 실행 순서와 승인 기준

| 단계 | 범위 | 다음 단계로 넘어가는 조건 |
| --- | --- | --- |
| 1. 데이터 신뢰성 | 카드별 상태·자산 수명·undo·저장 실패·마이그레이션 | A/B 독립성 및 삭제/교체 후 실제 이미지 복구 통과 |
| 2. 출력 계약 | 공통 레이아웃·텍스트 처리·내보내기 상태 | 다운로드 PNG의 글자·인원·비율·외곽선 비교 통과 |
| 3. 편집 경험 | 반응형 IA·공통 컨트롤·Pretendard·아이콘·모션 | 데스크톱/모바일 대표 작업을 화면 왕복과 가림 없이 수행 |
| 4. 배포 검수 | 실행 환경·공개 산출물·보안 경계·전체 결과 테스트 | 배포 디렉터리 스모크 검사 및 잔여 P0/P1 검토 완료 |

각 단계는 코드·비교 화면·사용자 시나리오 결과를 함께 제출한다. 일정은 1단계 자산 수명과 스키마 변경 범위가 확정되기 전에는 확약하지 않는다.

제품 검수는 새 사용자에게 이미지 추가 → 장비 연결 → 제목 수정 → PNG 저장을 수행하게 하고, 단계별 성공/막힘/되돌아감과 소요 시간을 기록한다. 현재 수치나 개선율을 만들어내지 않는다. 마케팅 관점의 우선 과제도 새 기능 홍보보다 ‘내 사진이 안전하게 저장되고 보이는 대로 나온다’는 약속을 실제로 충족하는 것이다.

## 7. 이번 제출의 한계

이번 제출물은 구현 전 제안서다. 제품 코드와 DESIGN.md를 수정하지 않았다. 기능 두 건은 브라우저로 재현했으며, 나머지는 코드·화면 근거와 추가 검증 필요성을 표시했다. 실제 iOS Safari/VoiceOver/NVDA, 운영 GPU 부하, 공개 배포는 실행하지 않았다. 새로운 발견이 있으므로 기존 ‘로컬 QA 게이트 완료’ 상태는 배포 승인 근거로 사용할 수 없다.
